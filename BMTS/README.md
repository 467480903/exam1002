# BMTS 与嵌入式总线基础

本文面向软考“系统架构设计师”和工业嵌入式开发，介绍 BMTS、现场总线、工业以太网及实时通信的基本概念。

## 1. 先区分三个概念

### 1.1 总线（Bus）

总线是多个设备共享的一组通信线路及其访问规则。它解决的是设备之间如何传输数据的问题，一般需要规定：

- 电气特性：电压、差分信号、终端电阻等；
- 帧格式：地址、数据、校验字段如何排列；
- 访问方式：哪个节点可以在什么时间发送；
- 错误处理：如何检测、确认、重传和隔离故障；
- 时序要求：速率、延迟、周期和同步精度。

### 1.2 通信协议

通信协议是通信双方共同遵守的规则。一个完整的工业通信系统可能同时包含物理层、数据链路层和应用层协议。

例如，Modbus RTU 可以使用 RS-485 作为物理传输方式：

```text
Modbus RTU：应用数据和报文规则
RS-485：差分电气接口
双绞线：物理传输介质
```

因此，RS-485 和 Modbus 不能简单地视为同一种东西。

### 1.3 BMTS

BMTS（Basic Message Transport Service，基本消息传输服务）是软考相关实时系统资料中的一种通信服务抽象，而不是可直接购买或部署的工业总线。

它位于上层功能和底层通信机制之间：

```text
请求—响应、文件传输、控制算法等上层功能
                    ↓
            BMTS 基本消息通信
                    ↓
 CAN FD / EtherCAT / Ethernet / 串口等执行机制
```

BMTS 的“窄腰”思想是：上层统一使用基本消息接口，底层通过适配器接入不同协议和硬件，从而降低系统耦合度。

> EtherCAT、CAN FD、MQTT、AFDX 和 TTE 都不是 BMTS；它们是具体协议或网络技术，其中一部分可作为 BMTS 的底层实现。

## 2. 总线通信的关键指标

### 2.1 带宽与有效吞吐量

- **带宽/标称速率**：总线理论上每秒能传输多少比特；
- **有效吞吐量**：扣除帧头、校验、仲裁、确认及空闲时间后，真正用于业务数据的速率。

标称速率高并不代表应用数据一定传得快。

### 2.2 延迟与抖动

- **延迟**：消息从发送端到接收端所花费的时间；
- **抖动**：多次传输的延迟变化幅度；
- **截止时间**：消息必须完成传输的最晚时间。

工业闭环控制不仅要求平均延迟低，还要求最坏情况延迟可预测。

### 2.3 实时性与确定性

“速度快”和“实时性强”不是同一个概念：

- 快：平均传输时间较短；
- 实时：能够在规定的截止时间内完成；
- 确定性：最坏情况延迟可以分析和约束。

普通以太网即使很快，也可能因排队和拥塞产生不确定延迟；实时工业以太网通常会增加时钟同步、时间片、优先级或流量调度机制。

### 2.4 可靠性

常见保障机制包括：

- CRC 校验；
- 应答与超时；
- 自动重传；
- 序号和重复检测；
- 双通道或环网冗余；
- 错误计数和故障节点隔离。

### 2.5 节点数、距离与拓扑

常见拓扑包括：

```text
总线型：节点挂接在一条主干线上
星型：所有节点连接到中央交换设备
环型：节点首尾连接，便于构造冗余路径
树型：多级交换或分支连接
```

速率、线缆长度、节点数量和抗干扰能力通常相互制约。

## 3. 总线访问与仲裁

多个节点共享介质时，必须解决“谁先发送”的问题。

### 主从/控制器—设备方式

由主站发起通信，从站按照要求响应。优点是行为容易预测，缺点是主站可能成为单点或性能瓶颈。

典型例子：传统 Modbus 主从通信、EtherCAT 主站周期扫描。

### 竞争与优先级仲裁

节点需要发送时参与竞争，由标识符或优先级决定谁先使用总线。

CAN 使用无损位仲裁，数值较小的报文标识符通常具有更高仲裁优先级。高优先级消息延迟较小，但持续高负载时低优先级消息可能长期等待。

### 时间片调度

系统预先分配发送时刻或时间槽，节点在规定时隙内发送。它便于分析最坏情况延迟，适用于确定性要求较高的系统。

## 4. BMTS 中的三类消息

### 4.1 事件触发消息

事件发生后发送，产生时刻通常不能提前确定。

```text
驱动器过温 → 立即发送报警消息
```

适合故障、报警、状态变化等信息。突发事件较多时需要处理竞争、拥塞和优先级问题。

### 4.2 速率约束消息

消息不必在固定时刻发送，但其发送频率、最小间隔或最大流量受到限制。

```text
设备状态最多每100 ms上报一次
```

速率约束可以控制带宽占用，避免某个节点持续发送而挤占其他消息。

### 4.3 时间触发消息

按照全局时间表，在指定时刻或时隙发送。

```text
每个控制周期开始后的第200 μs发送位置数据
```

它具有较好的确定性和可预测性，但需要时钟同步和预先调度，修改网络配置的成本也可能较高。

软考相关真题常列举的时间触发网络包括：

- AFDX：航空电子全双工交换式以太网；
- TTE：时间触发以太网。

## 5. AFDX：航空电子全双工交换式以太网

AFDX（Avionics Full-Duplex Switched Ethernet）是一种面向航空电子系统的确定性交换式以太网技术。它以标准以太网为基础，通过受控流量、冗余网络和确定性参数，使通信行为比普通办公以太网更容易预测。

典型结构如下：

```text
航空电子设备A ─┐                    ┌─ 航空电子设备C
               ├─ AFDX交换网络A ───┤
航空电子设备B ─┘                    └─ 航空电子设备D

航空电子设备A ─┐                    ┌─ 航空电子设备C
               ├─ AFDX交换网络B ───┤  ← 冗余网络
航空电子设备B ─┘                    └─ 航空电子设备D
```

### 5.1 核心概念

#### 端系统

端系统（End System）连接航空电子应用和AFDX网络，负责封装、发送、接收和检查数据帧。应用一般不直接操作交换机。

#### 虚拟链路

虚拟链路（Virtual Link，VL）是AFDX非常重要的逻辑单向通信通道：

```text
一个发送端 → 一个或多个接收端
```

每条虚拟链路可以预先配置允许的带宽、最大帧长度和发送间隔。网络据此限制各数据流，避免某个设备无限制地占用网络资源。

#### BAG

BAG（Bandwidth Allocation Gap，带宽分配间隔）用于约束一条虚拟链路连续发送帧的最小时间间隔。BAG越小，允许发送得越频繁，占用的预留带宽通常越多。

#### 双网冗余

AFDX通常使用相互独立的A、B两套网络发送相同帧。接收端接受先到且有效的副本，并丢弃重复帧。这样，一套网络或部分链路故障时，另一套网络仍可传输数据。

### 5.2 AFDX的主要特点

- 全双工交换通信，通常不会发生传统共享以太网的碰撞；
- 使用虚拟链路控制数据流向；
- 通过BAG等参数实施流量约束；
- 可以分析网络的最大传输延迟；
- 支持双网络冗余，提高容错能力；
- 主要用于航空电子设备之间的数据通信。

### 5.3 AFDX是不是严格的时间触发网络？

AFDX具有确定性和速率约束能力，但其基础机制更常被理解为**带宽受控、速率约束的确定性以太网**，并不等同于所有节点严格按照全局时间表占用时隙的纯时间触发协议。

在软考2018年相关案例的参考答案中，AFDX被列为“具有时间触发消息能力的网络总线”。考试时可以按参考答案填写；在工程讨论中，则应进一步区分“速率约束通信”和“严格的时间触发调度”。

## 6. TTE：时间触发以太网

TTE（Time-Triggered Ethernet）即时间触发以太网。它在以太网基础上引入全局时间同步和时间调度，使关键帧能够在预先规定的时刻发送，主要面向航空航天、交通控制和其他安全关键实时系统。

基本思想如下：

```text
全网时钟同步
      ↓
预先生成通信调度表
      ↓
关键节点在指定时刻发送
      ↓
交换机按照时间计划转发
```

### 6.1 TTE的三类通信流量

#### 时间触发流量（TT）

TT（Time-Triggered）帧在预先分配的时刻发送，具有最高的时间确定性，适合飞行控制、制动控制等关键周期数据。

```text
第0 ms：传感器A发送
第1 ms：控制器发送控制结果
第2 ms：执行器反馈状态
下一个周期重复
```

#### 速率约束流量（RC）

RC（Rate-Constrained）流量限制发送速率或最小发送间隔，但不要求每一帧都在完全固定的时刻发送。它适合对延迟有要求、但不需要严格时间片的状态数据。

#### 尽力而为流量（BE）

BE（Best-Effort）流量与普通以太网通信相似，使用剩余网络资源，通常不提供严格的延迟保证，适合维护、配置或非关键数据。

三类流量可以在同一物理网络中共存：

```text
TT：关键控制数据，按时间表传输
RC：受速率约束的实时数据
BE：普通非实时数据，使用剩余带宽
```

### 6.2 TTE的主要特点

- 各节点保持高精度的全局时间同步；
- 关键消息按照离线规划的时间表传输；
- 传输延迟和抖动更容易分析；
- 不同关键等级的流量可以在同一网络中共存；
- 可以通过冗余网络、冗余通道提高容错能力；
- 配置和调度设计比普通以太网复杂。

## 7. AFDX与TTE的区别

| 对比项 | AFDX | TTE |
|---|---|---|
| 中文名称 | 航空电子全双工交换式以太网 | 时间触发以太网 |
| 主要领域 | 航空电子网络 | 航空航天、交通及安全关键实时系统 |
| 核心机制 | 虚拟链路、BAG流量约束、双网冗余 | 全局时钟、时间表、时隙调度 |
| 确定性来源 | 预配置带宽和速率限制 | 在规定时刻发送和转发 |
| 主要流量模型 | 以速率约束的虚拟链路为核心 | TT、RC、BE三类流量共存 |
| 时间同步要求 | 不以全网严格时隙调度为核心 | 依赖高精度全局时间同步 |
| 时间抖动 | 可以约束，但并非严格固定时隙 | TT流量抖动通常更小、更可预测 |
| 配置复杂度 | 需要规划虚拟链路和带宽 | 还需要规划全网时间调度表 |

一句话区分：

> AFDX主要通过“限制每条虚拟链路能发多快”获得确定性；TTE主要通过“规定关键帧在什么时刻发送”获得确定性。

## 8. 常见嵌入式与工业通信技术

| 技术 | 类型和特点 | 常见用途 | 实时性说明 |
|---|---|---|---|
| UART | 点对点异步串行通信 | 调试口、模块通信 | 需由上层协议保证调度 |
| RS-485 | 差分电气接口，距离较远、抗干扰较强 | 工业仪表、Modbus RTU | 本身不定义应用层和实时调度 |
| I²C | 两线、地址化、板级低速总线 | 传感器、EEPROM | 通常用于单板内部 |
| SPI | 同步串行、全双工、速率较高 | ADC、Flash、显示器 | 主控制器调度，距离较短 |
| CAN | 多主、优先级仲裁、错误检测完善 | 汽车、工程机械、工业控制 | 事件触发，延迟可按优先级分析 |
| CAN FD | CAN 增强版，数据段最高64字节且可提高数据段速率 | 汽车与嵌入式控制 | 仲裁思想与 CAN 类似 |
| Modbus | 简单开放的工业应用协议 | PLC、仪表和上位机 | 实时能力取决于轮询周期和底层网络 |
| EtherCAT | 实时工业以太网、在途处理、分布式时钟 | 运动控制、伺服、分布式I/O | 周期短、同步精度高、确定性较强 |
| PROFINET | 工业以太网体系 | 自动化产线、PLC、驱动器 | 不同实时等级能力不同 |
| OPC UA | 信息建模、服务及安全通信 | 设备互联、边缘和上位系统 | 常规模式不等同于硬实时总线 |
| MQTT | 基于 Broker 的发布—订阅应用层协议 | 物联网、遥测、设备上云 | QoS 保证交付语义，不保证确定性截止时间 |
| DDS | 数据中心的发布—订阅中间件，QoS丰富 | 机器人、国防、实时分布式系统 | 可配置多种实时和可靠性策略 |
| TSN | 一组确定性以太网标准能力 | 融合工业网络、车载网络 | 提供时间同步和流量调度等机制 |

## 9. CAN FD 与 EtherCAT 的区别

| 项目 | CAN FD | EtherCAT |
|---|---|---|
| 网络基础 | CAN 总线 | 以太网物理层及专用工业协议 |
| 访问方式 | 多节点按报文优先级仲裁 | 主站组织周期通信 |
| 数据规模 | 单帧最多64字节有效载荷 | 适合在以太网帧中交换大量过程数据 |
| 典型拓扑 | 总线型 | 线型、树型、环型等 |
| 典型应用 | 车身控制、设备状态和分布式控制 | 多轴同步、伺服、机器人、快速I/O |
| 时间同步 | 通常依赖上层设计 | 支持分布式时钟 |
| 主要优势 | 成本低、可靠、实现普遍 | 周期短、吞吐量高、同步能力强 |

选型不能只比较峰值速率。例如少量控制器、报文短且成本敏感时，CAN FD可能更合适；多轴同步和大规模周期过程数据通常更适合EtherCAT。

## 10. 工业网络的分层示例

以一个带云端监控的运动控制系统为例：

```text
云平台
  ↑ MQTT/HTTPS：遥测、告警、远程管理
边缘网关或工控机
  ↑ OPC UA：设备信息模型和系统集成
控制器/PLC
  ↑ EtherCAT：确定性周期过程数据
伺服驱动器、编码器、分布式I/O
```

这些协议不是相互替代关系，而是在不同层次解决不同问题。不能因为 MQTT 能够传递消息，就用它直接替代硬实时运动控制总线。

## 11. 如何选择总线或协议

选型前应回答以下问题：

1. 最大和典型节点数是多少？
2. 报文大小、周期和突发流量是多少？
3. 可接受的最大延迟和抖动是多少？
4. 是否需要多个设备达到微秒级同步？
5. 线缆距离、拓扑和电磁环境如何？
6. 是否需要冗余、安全认证或功能安全？
7. MCU、控制器和操作系统是否有成熟协议栈？
8. 设备互操作、开发工具、诊断工具和授权成本如何？
9. 网络故障时应停止、降级还是继续运行？
10. 后续扩展和兼容旧设备有什么要求？

## 12. 软件架构中的实现方式

为了减少业务逻辑对具体总线的依赖，可以定义统一接口：

```cpp
struct Message {
    unsigned int id;
    const void* data;
    unsigned int length;
};

class MessageTransport {
public:
    virtual bool send(const Message& message) = 0;
    virtual bool receive(Message& message) = 0;
    virtual ~MessageTransport() = default;
};
```

然后针对不同协议实现适配器：

```text
MessageTransport
├── CanFdTransport
├── EtherCATTransport
├── MqttTransport
└── UdpTransport
```

这只是对 BMTS“统一通信抽象”思想的示意。实际项目还应处理线程安全、缓冲区所有权、优先级、超时、时间戳、重连和错误传播等问题。

## 13. 软考记忆要点

1. BMTS是通信服务抽象，不是具体总线协议。
2. 总线不仅包含线路，还涉及访问、仲裁、时序和错误处理规则。
3. 实时性强调在截止时间内完成；确定性强调最坏情况可以预测。
4. 事件触发看事件，速率约束看频率，时间触发看时刻或时隙。
5. CAN/CAN FD主要采用基于优先级的事件触发仲裁。
6. EtherCAT属于实时工业以太网，适合高速周期通信和设备同步。
7. MQTT的QoS不等于硬实时保证。
8. 2018年软考相关真题列举的时间触发网络是AFDX和TTE。

一句话总结：

> BMTS回答“上层需要怎样的统一消息服务”，具体总线和协议回答“消息最终通过什么规则和介质传出去”。
