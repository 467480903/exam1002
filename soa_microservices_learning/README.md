# SOA 与微服务学习示例

本目录包含试题参考答案和一个可运行的对比程序。示例把集团的电商、库存、支付、物流能力简化为一条订单链路，并分别用 **SOA + ESB** 和 **微服务 + 事件** 两种方式实现。

## 一、试题参考答案

### 问题 1：SOA 三大核心设计原则及其如何解决“信息孤岛”（9 分）

1. **服务契约（Service Contract）**
   - 含义：服务通过统一、明确且稳定的契约描述能力，包括接口地址、请求/响应格式、数据类型、错误码、安全和版本规则。调用者只依赖契约，不依赖服务内部使用 ERP、CRM 还是 WMS。
   - 解决问题：集团可为“查询客户”“创建订单”“扣减库存”等能力制定统一接口；旧系统通过适配器转换为标准消息，消除接口、协议和数据口径不一致造成的孤岛。

2. **服务松耦合（Loose Coupling）**
   - 含义：服务之间只保留最少依赖，通过契约、消息或中介通信，不了解对方内部实现；服务位置或实现变化尽量不影响调用者。
   - 解决问题：电商不再直接连接物流数据库，金融也不依赖某个 ERP 的表结构。ESB 负责路由、协议转换和消息转换，一个事业部升级系统时，其他事业部通常不必同步修改，从而减少流程断点。

3. **服务可重用性（Reusability）**
   - 含义：围绕稳定业务能力设计粗粒度、无特定渠道偏向的服务，使同一能力可被多个流程和事业部复用。
   - 解决问题：把各系统重复实现的客户认证、支付、库存查询、物流跟踪沉淀为共享服务。各事业部通过统一服务复用数据和能力，减少重复建设，并以同一数据源形成订单全链路视图。

**总结：**服务契约解决“如何一致地接入”，松耦合解决“如何独立变化”，可重用性解决“如何共享能力”。三者共同把封闭系统包装成可组合的企业服务，支撑跨部门流程协同和数据贯通。

### 问题 2：ESB 的核心功能（10 分）

企业服务总线（ESB）是 SOA 中连接服务消费者与提供者的集成中枢，核心功能包括：

1. **服务接入与适配**：连接 HTTP/SOAP、消息队列、文件、数据库及遗留系统。
2. **智能路由**：按服务名、消息内容、版本或规则把请求送至正确服务，可支持负载均衡。
3. **协议转换**：例如在 HTTP、SOAP、JMS 等协议之间转换。
4. **消息与数据转换**：统一字段、数据格式和企业数据模型，例如把 ERP 的 XML 转为 WMS 所需 JSON。
5. **服务编排**：按业务流程组合多个服务，完成订单、支付、库存和物流的跨系统协作。
6. **可靠消息传递**：提供队列、重试、持久化、幂等辅助和异常处理，降低消息丢失风险。
7. **安全与治理**：集中完成身份认证、授权、加密、限流、服务注册、版本和策略管理。
8. **监控与审计**：记录链路日志、性能指标和异常，支持故障定位、SLA 管理与合规审计。

因此，ESB 不只是“传消息”，还承担异构系统之间的连接、转换、路由、编排和治理。

### 问题 3：SOA 与微服务的主要区别（6 分）

| 维度 | SOA | 微服务架构 |
| --- | --- | --- |
| 服务粒度 | 通常较粗，面向企业级共享业务能力，可能组合多个子功能 | 通常较细，围绕单一业务能力和限界上下文，可独立部署 |
| 治理模式 | 偏集中治理；强调统一服务目录、企业数据模型、契约和 ESB 策略 | 偏自治、分散治理；团队负责服务全生命周期，允许按场景选择技术，但需遵守最小平台规范 |
| 技术异构性 | 能兼容大量遗留协议和异构系统，但常通过 ESB 统一转换，可能形成中心依赖 | 鼓励服务内部技术异构，常使用轻量 HTTP/gRPC/事件通信；每个服务独立数据存储、构建和发布 |

补充：二者不是简单的“旧与新”。微服务继承了 SOA 的服务化、契约和松耦合思想，更强调小团队自治、独立部署、去中心化数据与自动化运维。

## 二、运行示例

要求：Python 3.10+，无第三方依赖。

```bash
cd soa_microservices_learning

# SOA：请求交给 ESB，由 ESB 做协议转换和集中编排
python3 demo.py soa

# 微服务：订单服务调用库存/支付 API，再发布事件给物流服务
python3 demo.py microservices

# 自动运行两种模式并做基本断言
python3 -m unittest -v
```

运行时关注日志中的调用方向：

```text
SOA: 客户端 -> ESB -> 库存/支付/物流服务
微服务: 客户端 -> 订单服务 -> 库存/支付服务
                              -> 事件总线 -> 物流服务
```

## 三、代码阅读路线

1. 先看 `domain.py`：各业务能力没有依赖架构，是可复用的领域服务。
2. 再看 `soa.py`：`EnterpriseServiceBus` 集中承担契约适配、路由和业务编排。
3. 再看 `microservices.py`：每个服务拥有 API；订单服务负责自己的用例，事件总线异步通知物流。
4. 最后运行 `demo.py`，比较相同输入的日志和输出。

## 四、从示例到真实系统

本例为方便学习，所有组件运行在同一进程。生产环境会把服务拆为独立进程或容器，并补充 API 网关、服务发现、数据库隔离、鉴权、超时、重试、熔断、分布式追踪和消息中间件。尤其要注意：微服务不是“拆得越小越好”；当团队和业务规模不大时，模块化单体往往成本更低。
