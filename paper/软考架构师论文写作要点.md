# 软考系统架构设计师论文写作要点

## 1. 论文到底考什么

系统架构设计师论文不是普通技术文章，也不是项目工作总结。它主要考查考生能否：

1. 准确理解题目要求；
2. 以真实或合理的项目为背景；
3. 站在系统架构师角度分析问题；
4. 运用架构理论完成设计、分析和权衡；
5. 说明本人实际承担的工作；
6. 用问题、方案和效果证明设计具有可实施性。

官方考试目标强调：考生应能结合需求和约束设计合理架构，并对系统架构进行描述、分析、设计与评估。因此，论文的重点应当是**架构决策及其依据**，而不是只介绍技术名词或项目管理过程。

一句话概括：

> 论文要回答“我在什么项目中，面对什么问题，为什么选择这种架构，如何落地，解决了什么问题，最终效果如何”。

## 2. 考试基本认识

现行系统架构设计师考试大纲为2022年审定版本，论文科目采用给定若干专题、选择其中一个进行写作的形式。相关备考资料通常将论文考试时间概括为120分钟，练习时应以不少于2500字为目标；实际考试形式、字数提示和输入限制应以当次考试系统及官方通知为准。

论文题目通常由“论题＋若干子问题”组成。例如：

```text
论智能信息系统的开发与应用

1. 概要叙述项目以及本人承担的主要工作；
2. 结合项目介绍采用的关键技术；
3. 说明如何设计与实现，并分析实际问题和解决方案。
```

评分时不仅看文章是否通顺，更看是否逐项回答了题目给出的子问题。

## 3. 选题原则

看到多个题目后，应优先选择同时满足以下条件的题目：

- 有比较熟悉的真实项目背景；
- 本人在项目中具有架构设计或关键决策职责；
- 能列出至少三项具体架构决策；
- 能写出两个以上实际问题及解决过程；
- 能提供合理的效果或评价结果；
- 项目经历能够覆盖题目所有子问。

不要只因为熟悉某个技术名词就选择题目。例如，了解微服务的定义，并不代表能够写好“论微服务架构设计”。还必须能够说明：

```text
为什么拆分服务？
按什么边界拆分？
如何处理通信、事务、容错和监控？
遇到什么问题？
采取方案后效果怎样？
```

## 4. 审题方法

审题时先圈出四类关键词。

### 4.1 论题对象

例如：

- 云原生架构；
- 微服务架构；
- 系统可靠性；
- 安全架构；
- 智能信息系统；
- 软件架构评估；
- 嵌入式系统架构。

全文必须围绕这个对象展开，不能写着写着变成一般项目管理论文。

### 4.2 题目要求的理论

例如题目要求：

- 介绍关键技术；
- 说明架构风格；
- 分析质量属性；
- 论述设计方法；
- 描述评价过程。

这些理论内容必须在正文中明确出现，并和项目实践结合。

### 4.3 子问题

把每个子问题直接转换成正文一级标题，最安全：

```text
子问1 → 项目概况及本人工作
子问2 → 理论、方法或关键技术
子问3 → 项目中的设计、实施、问题及解决
```

### 4.4 限定词

特别注意：

- “结合实际项目”；
- “详细说明”；
- “分析原因”；
- “比较优缺点”；
- “说明取得的效果”；
- “本人承担的工作”。

如果题目要求比较两种方案，只写最终方案就不完整；如果要求分析问题，只列解决方案而不写原因，也不完整。

## 5. 推荐的论文结构

建议采用以下稳定结构：

```text
题目
摘要
正文
  一、项目背景及本人职责
  二、理论、方法或关键技术
  三、系统架构设计与实现
  四、实际问题、架构权衡与解决方案
  五、项目效果与经验总结
结语
```

如果题目只有三个子问，也可以把正文严格写成三个对应章节。结构不是越复杂越好，关键是阅卷人员能够快速找到答案。

## 6. 摘要怎么写

摘要应当是全文的压缩版，一般包括：

1. 项目时间与背景；
2. 项目目标和业务范围；
3. 本人角色；
4. 核心架构或关键技术；
5. 主要问题和解决办法；
6. 项目结果；
7. 点明论文主题。

推荐模板：

> 某年某月，我所在单位启动了某系统建设项目。该系统主要用于……，需要满足……等要求。我在项目中担任系统架构师/项目负责人，负责需求分析、总体架构设计、技术选型和关键问题解决。项目采用……架构，并使用……技术实现……。针对实施中出现的……问题，我组织团队采用……方案解决。系统最终……。本文结合该项目，重点论述……的设计、实施及应用效果。

摘要要避免：

- 大段解释概念；
- 只写行业背景，不写项目；
- 只写“本文首先、其次、最后”；
- 出现正文没有论证的新结论；
- 使用空泛的“效果良好、得到一致好评”。

## 7. 项目背景怎么写

背景部分需要让阅卷人员快速相信这是一个可以落地的项目。至少说明：

- 建设单位或行业；
- 建设原因；
- 系统用户；
- 核心业务；
- 系统规模；
- 关键非功能要求；
- 项目周期；
- 本人角色及职责。

可以写合理的规模数据，例如：

```text
系统服务多少用户；
包含多少个主要模块；
正常和峰值并发量；
数据规模；
部署节点数量；
可用性、响应时间或恢复时间要求。
```

数据必须前后一致。例如前文写日请求量10万，后文不能突然写峰值100万QPS。

## 8. 如何体现“我是架构师”

论文中必须明确使用第一人称说明本人工作，例如：

- 我组织了需求和质量属性分析；
- 我主持了总体架构设计；
- 我比较了多个候选方案；
- 我确定了服务边界和数据策略；
- 我制定了容错、安全和部署方案；
- 我组织了架构评审；
- 我针对实施问题调整了架构。

避免全文只出现：

```text
项目组采用了……
系统实现了……
公司决定了……
```

这种写法看不出考生本人做了什么。但也不能把所有事情都写成自己一个人完成，应体现组织、决策、协调和指导作用。

## 9. 技术理论怎么写

理论部分不能只是教材定义，也不能完全跳过理论直接讲故事。推荐采用“定义—特点—适用性—项目映射”的结构。

例如写微服务：

```text
定义：将系统拆分为围绕业务能力的小型自治服务。
特点：独立部署、松耦合、服务间通信、分散治理。
适用性：适合业务复杂、团队较多、需要独立扩展的系统。
项目映射：本项目按照订单、库存、支付等业务边界拆分服务。
```

例如写智能信息系统：

```text
定义：以人工智能、数据和感知技术增强信息处理与决策能力。
关键技术：数据采集、模型训练、推理、知识表示、智能决策。
项目映射：使用VLA模型根据视觉观察和任务指令生成机器人动作。
```

理论篇幅不宜过长。论文的重点不是背诵教材，而是证明能够把理论应用到架构设计中。

## 10. 架构设计要写到什么程度

架构部分应回答以下问题：

```text
系统分成哪些层、模块、服务或节点？
各部分承担什么职责？
它们如何通信？
数据存放在哪里？
关键业务如何流转？
如何满足性能、可用性、安全性和可修改性？
为什么选择该方案，而不是其他方案？
```

可以采用分层方式描述：

```text
接入层
业务服务层
智能推理或领域服务层
数据层
基础设施层
运维与安全体系
```

也可以按照关键视图描述：

- 逻辑视图：模块和职责；
- 进程视图：运行时进程和通信；
- 开发视图：代码、构件和依赖；
- 物理视图：节点和部署；
- 场景视图：核心业务流程。

不要求在论文中把所有视图都写完，应围绕题目选择最有解释力的内容。

## 11. 写好架构决策

一项有说服力的架构决策至少包含：

```text
业务或质量要求
      ↓
候选方案
      ↓
约束与权衡
      ↓
最终选择
      ↓
具体实现
      ↓
验证效果
```

示例：

> 铝条较长，项目初期采用双臂协同抓取，但双臂动作空间维度高，示教数据不足，且两臂误差容易通过工件相互耦合，导致推理稳定性较差。经过对比，我决定改用单臂推理，并设计适配铝条截面的专用夹爪。该方案降低了模型输出维度，利用机械导向扩大抓取容差，使智能推理与确定性机械约束形成互补。

这段话同时包含问题、原因、权衡、决策和效果，比“我们改成了单臂方案”更有得分价值。

## 12. 质量属性要具体化

不要只写：

```text
系统具有高性能、高可用、高安全性和良好扩展性。
```

应写成可以验证的质量属性场景：

```text
正常负载下，95%的查询请求在2秒内返回；
主节点失效后，系统在30秒内完成故障切换；
新增一种设备协议时，仅需开发适配器，不修改核心业务模块；
未授权用户不能读取生产数据，所有管理操作保留审计记录。
```

质量属性场景可按六要素组织：

```text
刺激源 → 刺激 → 环境 → 制品 → 响应 → 响应度量
```

## 13. 问题与解决方案怎么写

论文至少准备两到三个有技术含量的问题。每个问题建议按照以下结构展开：

### 13.1 现象

系统出现了什么具体问题？

### 13.2 原因

为什么会出现？涉及哪些架构、数据、算法、网络或资源因素？

### 13.3 候选方案

有哪些可能的解决方式？各自代价是什么？

### 13.4 最终决策

为什么选择当前方案？牺牲了什么，获得了什么？

### 13.5 实施措施

具体修改了哪些模块、接口、配置、机械结构或部署策略？

### 13.6 验证结果

通过测试、监控、评审或业务指标证明问题得到改善。

常见无效写法：

> 系统出现性能问题，经过大家共同努力，最终解决了问题。

有效写法应说明瓶颈位置、原因、选型和结果。

## 14. 要体现架构权衡

架构设计很少存在只有优点的方案。主动写出取舍，会更像架构师论文。

例如：

- 缓存提高性能，但增加数据一致性复杂度；
- 冗余提高可用性，但增加成本和同步开销；
- 微服务便于独立扩展，但增加网络调用与运维复杂度；
- 通用夹爪适应任务较多，但特定任务抓取稳定性不足；
- 专用夹爪提高可靠性，但降低通用性；
- 强一致性减少数据冲突，但网络分区时可能牺牲可用性；
- VLA模型提高环境适应能力，但输出确定性低于传统固定程序。

典型表达：

> 在通用性和现场可靠性之间权衡后，我们在POC阶段采用专用夹爪，将通用能力限制在合理范围，以换取更大的机械容差和更稳定的任务完成效果。

## 15. 项目结果怎么写

结果应尽量可验证，可从以下方面说明：

- 功能验收；
- 性能测试；
- 故障恢复测试；
- 安全测试；
- 用户或业务部门验收；
- 运行周期；
- 成本或效率变化；
- 团队能力和可复用资产。

不能捏造不了解的数据。如果项目仍是POC，可诚实写：

> 项目完成了从数据采集、模型训练、边缘推理到机器人执行的闭环验证，证明了方案的技术可行性，但在异常场景覆盖和长期运行稳定性方面仍需继续完善。

这种表述比虚构“上线后效率提升80%”更可信。

## 16. 结语怎么写

结语通常包含：

1. 回顾本人完成的核心架构工作；
2. 概括项目效果；
3. 说明不足；
4. 提出后续改进方向；
5. 回扣论文主题。

推荐模板：

> 通过本项目，我组织团队完成了……的架构设计与实施，并利用……解决了……问题。系统最终实现了……。实践表明，……是项目成功的关键。但系统在……方面仍有不足，后续将通过……进一步改进。本项目为企业后续同类系统建设提供了可复用的架构和经验。

## 17. 字数和篇幅分配建议

练习时可按约2500～3000字规划，具体以当次考试要求为准：

| 部分 | 建议占比 |
|---|---:|
| 摘要 | 约10% |
| 项目背景和本人职责 | 约15% |
| 理论和关键技术 | 约15%～20% |
| 架构设计与实施 | 约30%～35% |
| 问题、权衡和解决方案 | 约20%～25% |
| 效果与结语 | 约10% |

核心原则：

> 项目背景够用即可，把主要篇幅留给架构设计、技术应用、问题分析和解决效果。

## 18. 120分钟时间安排建议

| 时间 | 工作 |
|---:|---|
| 0～10分钟 | 阅读全部题目，选择最熟悉的项目和论题 |
| 10～20分钟 | 写提纲，建立子问与章节对应关系 |
| 20～35分钟 | 完成摘要和项目背景 |
| 35～95分钟 | 完成理论、架构设计、问题与解决方案 |
| 95～110分钟 | 完成效果总结和结语 |
| 110～120分钟 | 检查漏答、逻辑、错别字和前后数据 |

如果打字速度较慢，应在平时练习完整论文，而不是只背提纲。

## 19. 机考写作注意事项

- 先写完整提纲再展开，防止后半篇偏题；
- 使用清晰的小标题；
- 技术名词首次出现时写中文含义；
- 段落不宜过长；
- 不要依赖复杂表格、图片和公式；
- 不频繁删除大段内容，避免时间不足；
- 随时关注剩余时间和字数提示；
- 保存前检查标题、摘要和正文是否完整。

## 20. 常见失分原因

### 20.1 偏题或漏答子问

全文技术内容很多，但没有回答题目明确要求的比较、评价或问题分析。

### 20.2 写成项目管理论文

大量描述立项、进度、会议、人员和成本，架构设计内容过少。

### 20.3 写成教材定义

只介绍概念、特点和优缺点，没有真实项目映射。

### 20.4 堆砌技术名词

罗列微服务、容器、消息队列、AI、大数据等技术，却没有说明为什么使用、如何组合和解决什么问题。

### 20.5 本人角色不清楚

看不出考生是否参与架构设计，只像项目旁观者。

### 20.6 项目内容前后矛盾

包括时间、规模、技术、角色、部署方式和指标不一致。

### 20.7 方案缺乏权衡

所有技术都只有优点，没有成本、风险和适用边界。

### 20.8 结果空泛

只写“系统取得良好效果”，没有测试、验收或实际表现。

### 20.9 项目过于宏大

短期POC却描述为全国性生产系统，个人承担全部算法、机械、电气和软件工作，可信度较低。

### 20.10 过度暴露不专业表达

正式论文中，应把“高层强推”“自己掏钱找人”等口语，改写为：

```text
公司将机器人智能化列为年度重点任务；
我协调外部高校专家开展专项技术指导；
为弥补团队经验不足，引入外部专家进行流程带教。
```

既保留事实，也体现管理和架构职责。

## 21. 技术名称的使用原则

技术名词应服务于架构论证。例如写VLA模型时，不能只写使用了GR00T、π0.5和Linbot，还应说明：

- 模型输入是什么；
- 模型输出是什么；
- 如何采集训练数据；
- 如何连接机器人控制器；
- 为什么选择主模型；
- 如何限制模型输出风险；
- 出现推理失败时如何降级和恢复。

如果不能解释某项技术如何落地，宁可少写，也不要堆砌。

## 22. 可以提前准备的项目素材

建议为每个候选项目准备一张素材卡：

```text
项目名称：
时间和周期：
建设单位和行业：
本人角色：
用户和业务范围：
系统规模：
关键质量属性：
总体架构：
核心技术：
三个架构决策：
三个实际问题：
解决方案及权衡：
测试和验收结果：
不足和改进方向：
```

同一项目可以根据不同题目调整重点，但不能生硬套用。例如机器人项目可分别用于：

- 智能信息系统；
- 嵌入式或边缘计算架构；
- 系统可靠性设计；
- 软件架构质量属性；
- 架构演化；
- 系统安全设计。

每个题目的理论主线和架构重点必须重新组织。

## 23. 通用提纲模板

```text
# 论……

## 摘要
项目、角色、核心技术、问题、方案、结果、点题。

## 一、项目概况及本人工作
业务背景、系统范围、规模、约束、质量要求、本人职责。

## 二、相关理论与技术
定义、核心内容、特点、适用性，并映射到本项目。

## 三、总体架构设计
分层/服务/节点、职责、通信、数据、部署和安全。

## 四、关键架构决策
需求、候选方案、权衡、最终选择和实现方法。

## 五、问题及解决方案
问题现象、原因、解决措施、验证结果。

## 六、项目效果与总结
验收、指标、经验、不足和后续改进。
```

## 24. 考场最终检查清单

提交前逐项检查：

- [ ] 标题是否与所选题目一致；
- [ ] 摘要是否包含项目、角色、技术、问题和结果；
- [ ] 是否逐项回答所有子问题；
- [ ] 是否明确写出本人职责；
- [ ] 是否以架构设计为主，而不是项目管理流水账；
- [ ] 是否有总体架构及模块职责；
- [ ] 是否写清至少两项架构决策；
- [ ] 是否包含方案比较和质量属性权衡；
- [ ] 是否有两个以上实际问题及解决办法；
- [ ] 是否说明测试、验收或应用效果；
- [ ] 项目时间、规模、技术和指标是否前后一致；
- [ ] 是否避免捏造无法自圆其说的数据；
- [ ] 是否说明项目不足和改进方向；
- [ ] 是否达到考试系统要求的字数；
- [ ] 是否留出时间检查错别字和病句。

## 25. 对当前VLA机器人论文的针对性建议

当前《智能信息系统的开发与应用》论文已经具备较好的项目真实性和问题素材，后续优化时应重点注意：

1. 保留“本人主导架构与决策”的主线；
2. 将专家支持表述为外部技术咨询和知识转移；
3. 补充项目规模、周期、数据规模和测试方法，但不虚构指标；
4. 明确VLA输入、输出、训练与推理部署流程；
5. 强调“VLA＋状态机＋安全约束＋机械结构”的混合架构；
6. 将双臂改单臂写成复杂度与可靠性的架构权衡；
7. 将通用夹爪改专用夹爪写成通用性与稳定性的权衡；
8. 将二次定位写成软件智能与机械确定性协同；
9. 明确项目仍处于POC阶段，避免把验证成果夸大为生产级效果；
10. 根据正式题目的三个子问重新压缩到考试要求的篇幅。

## 26. 最重要的写作原则

> 不要证明自己知道很多技术名词，要证明自己能够根据需求和约束作出合理的架构决策，并能对决策结果负责。

一篇合格的论文应形成完整闭环：

```text
项目需求
   ↓
架构分析
   ↓
方案选择与权衡
   ↓
设计和实施
   ↓
问题与调整
   ↓
测试和效果
   ↓
经验与改进
```
